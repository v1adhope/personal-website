---
title: "Why Microservices Fail: Lessons from My Practice"
pubDate: 2025-10-05
description: "The decisions that turn microservices into distributed legacy."
tags: ["softwareArchitecture", "microservices"]
---

I've noted these reasons in my own practice and observed cases where microservices are literally micro: a single function.

- Running away from spaghetti code to start fresh (spoiler: it's better to improve the old code than start over).

- A language salad. Some services use language A, others B, and others C. An engineer decides to write a new service because they love language B and think the job will be done sooner.

- A lack of knowledge, documentation, and expertise. Working with the unknown, stepping on rakes, and fixing things later.

- Wrong decisions lead to more wrong decisions. A service isn't designed around DDD and is named after technology A or integration A. That leads to service B, but they do the same things and duplicate each other.

- Planning too far ahead.

Fixing legacy code in one repository is simpler than fixing distributed legacy code.
