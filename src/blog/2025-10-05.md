I noted reasons in my practice and what I observed where micro services are a literally micro (a function):

- Run away from spaghetti code and start writing clear from scratch (spoiler: better improve old than start a new)

- Languages salad. Part services on language A, second on B, and third on C. The Engineer decided to write a new service, because they love the B language, and job will be done early

- Lack of knowledge, documents, and expertise. Working with unknown, catch rakes, and fix later

- Wrong decisions produce new ones. Service created not by DDD and was named as a tech A/ integration name A. That will provide service B, but they do the same things and duplicate each other

- To plan too far

Fixing legacy in one repository is simpler than distributed legacy
